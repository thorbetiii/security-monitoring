Scenario status: VALIDATED AND COMPLETE
Formal experiment date: 26 June 2026

===============================================================================
1. SCENARIO OBJECTIVE
===============================================================================

The purpose of this scenario was to test whether application-log anomaly
detection could identify repeated, technically valid checkout operations that
did not create a conventional infrastructure incident.

The workload repeatedly completed the legitimate application workflow:

1. GET a valid product page
2. POST the product to the cart
3. GET the cart
4. POST /cart/checkout with valid customer and payment-form data

The attack did not use malformed requests, invalid credentials, endpoint
scanning, or high-volume generic flooding. It represented abuse of a valid
business operation.

===============================================================================
3. FIXED WORKLOAD CONFIGURATION
===============================================================================

Normal workload:
- 2 persistent Locust users
- Each user maintained its own HTTP session and cookie jar
- Wait time: 60–90 seconds
- Normal traffic ran continuously throughout the experiment

Checkout-abuse workload:
- 5 persistent Locust users
- Spawn rate: 1 user/second
- Wait time: 3–5 seconds
- Duration: 5 minutes
- Each user repeatedly completed the full valid checkout workflow

The attack intensity was frozen after pilot validation and was not changed
between the three formal runs.

===============================================================================
4. FORMAL EXPERIMENT PROTOCOL
===============================================================================

Each formal run used the following sequence:

- 10 minutes normal preconditioning, not included in the measured result
- 10 minutes measured normal baseline
- 5 minutes normal traffic plus checkout-abuse traffic
- 10 minutes measured normal recovery

The two normal users remained active across all phases. The five abuse users
were added only during the attack phase.

This continuous-baseline method avoided artificial zero-traffic gaps between
baseline, attack, and recovery.

Formal runs included in the final dataset:
- Run 01
- Run 02
- Run 03

Earlier orchestration failures were archived separately and excluded because
the complete formal protocol did not finish. They were not included in any
detection-rate or performance calculation.

===============================================================================
7. INTERPRETATION
===============================================================================

The checkout-abuse workload caused a large change in business-operation
frequency without causing an infrastructure outage or conventional resource
incident.

The checkout rate increased by approximately 48 times relative to the normal
baseline, but:

- all requests succeeded;
- checkout latency remained stable;
- all pods remained ready;
- no container restart count increased;
- no CPU, memory, restart, or readiness alert fired.

AD-04R detected the attack onset in all three formal runs. The detector was
primarily influenced by checkout_count, with attribution between 87.34% and
90.12%. The unique-session feature also contributed, but to a smaller degree.

Run 02 showed that the detector could still identify abnormal checkout
frequency even when the observed session count matched the model’s expected
session count. This indicates that the checkout-frequency feature was
independently useful.

Run 03 produced a lower anomaly grade of 0.6875 while still producing a
positive result with high confidence. One possible explanation is partial
adaptation of the online Random Cut Forest model after repeated exposure to a
similar pattern. This is a plausible interpretation, not a separately proven
cause.

The detector flagged the onset of the behavioral transition. Later high-rate
intervals generally received grade zero because they represented continued
instances of the same already-observed attack state rather than new
transitions.

===============================================================================
8. FINAL CONCLUSION
===============================================================================

The checkout-workflow anomaly detector successfully detected business-logic
abuse in 3 of 3 formal runs, giving a 100% formal detection rate.

The scenario demonstrated that repeated valid checkout operations can remain
below infrastructure-alert thresholds while still representing abnormal
application behavior.

The main experimental conclusion is:

Application-log behavioral anomaly detection identified repeated,
legitimate-looking checkout operations that conventional CPU, memory,
restart, and readiness monitoring did not classify as infrastructure
incidents.

This result supports the use of OpenSearch anomaly detection as a complement
to Prometheus and Grafana monitoring. Grafana remained useful for confirming
system health and availability, while AD-04R provided visibility into abnormal
business-workflow behavior.
